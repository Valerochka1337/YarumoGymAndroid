# Локальная проверка и будущая оценка AI

Внешний inference не запускался. Все данные синтетические. Unit/integration tests проверяют передачу данных, арифметику, ограничения, сохранение и fencing, но не доказывают качество решений модели. Потеря истории в исходном пользовательском случае не доказана; параметры того запроса не восстановлены.

## Спецификация planner-duration-v1

Секунды = сумма durationSec для timed/cardio и 45 секунд для каждого силового подхода + restSeconds между подходами одного упражнения (N−1; null = 90) + 90 секунд между упражнениями (E−1). После последнего подхода/упражнения дополнительного отдыха нет. Все промежуточные вычисления целочисленные Long, минуты округляются до ближайшей: (seconds+30)/60. Оценка приблизительная: темп, ожидание оборудования и незапланированная разминка неизвестны.

Разминка учитывается только явно перечисленными подходами, один раз; фиксированные «ещё 5/10 минут» не прибавляются. Prompt требует не добавлять разминку мысленно. В принятой программе AI сохраняет явный отдых (null модели материализуется как 90), поэтому изменение пользовательского default rest не меняет её оценку. Для прочих программ null использует фактическую настройку отдыха Android; при default=90 fixtures совпадают с backend.

Желаемое время сохраняет wire-имя `availableDurationMinutes`: запрос/долговечные байты не изменяются. Коридор [desired*60 − max(300, desired*12), desired*60]. 30 → 24–30, 60 → 48–60, 90 → 72–90 минут. Это инженерный критерий существенного недобора, не медицинская норма. Верхняя граница прежнего клиента сохранена. Backend отвергает превышение полной оценки, а не только timed+rest.

При недоборе и ≥6 выбранных кандидатов, отсутствии текстовых ограничений и остатке lease >20 секунд допускается одна коррекция. Максимум 2 вызова на одну попытку, второй получает ≤20 секунд и не выходит за оставшийся общий 45-секундный срок. Автоматический объём, повторы или отдых ради заполнения времени не добавляются. Если исправленный результат всё ещё короткий, он публикуется с reason code. Непроверяемый ответ/истечение срока сохраняют штатную ошибку, не создают предложение. Существующие durable job recovery (до 3 исполнений при потерянном lease) не изменены.

## Контракт и выкат

1. Backend: SQL `017-planner-explanations.sql` и код. Пояснение сохраняется атомарно с версией предложения; FK обеспечивает удаление вместе с ней.
2. Неизменные `/training-proposals`, `/ai/calendar-drafts`, job responses и approval DTO продолжают обслуживать старые строгие клиенты.
3. Новый GET `/v1/training-proposals/{proposalId}/planner-explanation` возвращает только пояснение текущей версии получателю. 404 — старая запись/нет пояснения; чужой ID также скрывается. ID/version, целевое/расчётное время, минимум, состав фокуса, пересечение с последней историей вычисляет backend. Модель выбирает только enum причины; дат, чисел, ссылок и свободного текста в rationale нет. Android повторно проверяет identity/version, арифметику, типы и ссылки на упражнения исходного snapshot.
4. Затем Android 1.3.61 (69). Новый клиент с прежним сервером работает без пояснения. Пояснение подгружается отдельно и хранится только в памяти экрана: офлайн оно недоступно, существующая подготовка/черновик/очередь принятия остаются работоспособны. Ошибка optional GET не блокирует план. Редактирование скрывает исходное обоснование и пересчитывает время.
5. Перед публикацией обеих веток заново fetch main и проверить версии: соседнее исправление updater также повышает версию. Сейчас зарезервирован только один инкремент. Push/PR/merge/deploy не выполнялись.

## Рубрика будущего сравнения v2 / v3

Фиксировать model/version, параметры, одинаковый обезличенный контекст, JSON ответа, количество вызовов, оценку backend и время ответа. В этом задании платный/внешний запуск не разрешён. Приложенные `planner-sequence-duration-ai-fixtures.json` — вручную подготовленные ответы для воспроизводимых проверок, не результаты модели; baseline намеренно содержит недобор.

Оценивать каждый пункт 0/1/2 (нарушение / частично / выполнено), не складывать провал жёстких ограничений с удачными баллами:

| Критерий | Проверка |
|---|---|
| История | Последняя дата и выполненные факты доступны; weekly и recent не суммируются со сводкой/ссылками повторно. Пустая история не превращается в «никогда не тренировался». |
| Последовательность | Акцент соответствует цели, частоте занятий, пожеланиям и последним тренировкам. Повтор допустим с осмысленной причиной; разнообразие само по себе не цель. |
| Время | 30/60/90: расчёт в коридоре при достаточном наборе. Короткий план явно объяснён; не набраны произвольные подходы/повторы/отдых. |
| Ограниченный зал | Используются только доступные варианты; недобор не скрыт и не объявлен доказанной невозможностью. |
| Пояснение | Причины согласованы с планом, повторы вычислены по истории, числа только backend. Нет выводов о восстановлении/травмах по интервалу. |
| Стоимость | Не более двух вызовов в одной попытке; повтор HTTP с тем же requestId не вызывает генерацию заново. |

Минимальные сценарии: пустая история; последняя тренировка с верхом/трицепсом + приоритет ног; явный приоритет повторить упражнение; ограниченный зал с двумя упражнениями; текстовое ограничение; 30/60/90; timed/cardio и явно включённая разминка. Хороший ответ не обязан содержать конкретные упражнения из fixture — качество выбора требует отдельного eval.

## Ручная проверка после разрешённого выката

1. Синтетический аккаунт: создать завершённую тренировку, две доступные программы/группы упражнений, синхронизировать; запросить 60 минут. Проверить фактическую оценку и обоснование, а не название программы.
2. Повторить для пустой истории и 30/90 минут; ограничить зал двумя упражнениями — короткий результат должен объяснять недобор.
3. Открыть старое предложение: всё работает без пояснения. Отключить сеть после получения подготовки: открыть сохранённый план и сохранить правку; очередь принятия сохраняется.
4. Изменить подход/отдых: время пересчитано, старое обоснование скрыто. Вернуть исходный вариант — пояснение снова относится к нему.
5. Принять план явно; оценка на карточке программы совпадает. Сменить аккаунт во время загрузки пояснения: поздний ответ не появляется.

Скриншоты, телефон, реальные пользовательские AI-запросы и production не использовались.

## Доказательства и границы

`planner-duration-v1.json` в обоих репозиториях совпадает побайтно (SHA-256 `4f2823682145473aaad5343a8d8483d8a8745b768de6efa30e97cb694cf44dbf`). Фокус — топ-3 по текущей карте вкладов мышц, умноженных на число плановых подходов; UI подписывает его «по составу». Это не физиологическая доза и не восстановление. Отсутствие реального eval означает, что улучшение качества выбора акцента остаётся гипотезой до сравнения реальных ответов на синтетическом наборе.

Локальная release/R8-сборка не входит в выполненные проверки: текущий `app/build.gradle.kts` требует release-подпись; секреты и signing-конфигурация не использовались. Обязательные debug/unit-проверки выполняются без production и без устройства.
