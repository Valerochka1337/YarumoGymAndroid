# ValerochkaGym — архитектура

Android-клиент персональных аккаунтов backend для силовых тренировок. Один Gradle-модуль `:app`,
пакеты по слоям. Android 16+ (minSdk 36, targetSdk 37), Kotlin + Jetpack Compose
(Material 3 Expressive), Hilt, Room, DataStore, WorkManager, Retrofit.

## Слои

Авторегуляция Live Coach: чистые правила в `domain/autoregulation`, интеграция через
`CoachWorkoutReader`, `CoachToolCodec`, `CoachConversationService` и существующий
`WorkoutEditor`/`WorkoutWriteQueue`. Nullable RIR хранится в подходах (Room 31), portable
снимках и undo. Расчётный пакет проверяет факты повторно перед подтверждением; обновление
ожидающего расчёта создаёт новый UUID предложения. Основания и границы правил —
[docs/autoregulation.md](docs/autoregulation.md).
Диагностика Live Coach: debug-события через `CoachDiagnostics` с тегом `LiveCoach`;
этапы, расчёты, причины решений и ошибки описаны в
[docs/live-coach-diagnostics.md](docs/live-coach-diagnostics.md).

```
ui/        экраны (Compose) + ViewModel'и; exercise/ (карточка упражнения и статистика),
           gyms/ (каталог залов и их оборудования),
           theme/ (Material You, light/dark схемы, форма, типографика, GymMotion), haptics/ (GymHaptics),
           components/ (GymCard, PillButton, GymFilterChip, …)
domain/    use case'ы и чистая логика (WorkoutEditor, WorkoutRowParser,
           ExerciseStatisticsCalculator, analysis/AnalyticsEngine — математика аналитики)
data/      Room (db/), Google-интеграция (google/), AI-генератор (ai/), настройки
           и зашифрованный ключ (settings/), резервные операции (backup/), иконка лаунчера (appicon/)
service/   WorkoutSessionService (foreground) + RestTimerEngine
worker/    UploadWorkoutWorker + UploadScheduler, UploadMeasurementWorker + MeasurementUploadScheduler,
           UploadRoutineWorker + RoutineUploadScheduler, UploadConfigurationWorker (WorkManager)
di/        Hilt-модули (Data, Domain, Google, Network) и квалификаторы
           (@ApplicationScope, @ComputeDispatcher)
```

## Потоки данных

- **Room → Flow → ViewModel → Compose.** ViewModel'и собирают состояние `combine(...)` +
  `stateIn(viewModelScope, WhileSubscribed(5000), initial)`; nullable-списки отличают
  «не загружено» от «пусто», one-shot события идут через `Channel(BUFFERED).receiveAsFlow()`.
- **Порядок упражнений активной сессии.** `WorkoutExerciseEntity.position` — персистентный порядок
  только текущей тренировки. Пока пользователь тянет grip, экран держит локальный список id и
  меняет его синхронно на каждом crossing; после отпускания репозиторий одной транзакцией
  проверяет полный уникальный набор id и перенумеровывает позиции. Исходная программа не меняется;
  её может обновить только подтверждение по факту в итогах тренировки.
- **Оборудование и ограничение по залам.** Зал хранит выбранные виды оборудования,
  упражнение — совместные требования. Доступность означает покрытие всех требований каждым
  выбранным залом; пустой набор залов оставляет полный каталог. Возможности регулируемой
  скамьи покрывают горизонтальный и положительный наклон; отрицательный требует явно подходящей
  опоры. «Без оборудования» отличается от неизвестных требований старого своего упражнения.
  Старые залы сохраняют `GymExerciseEntity` до явного успешного сохранения оснащения.
  Picker и предупреждения редактора программы используют один reactive поток
  `GymRepository.observeAvailableExercises`; прежний список связей не определяет доступность
  настроенного зала.
  Сохранение зала, требований упражнения, программы и старт тренировки проверяют доступность
  атомарно: конфликт показывает затронутые упражнения и не удаляет строки или подходы.
  При старте связи программы с залами копируются в `WorkoutGymEntity`; завершённая история
  не переписывается при изменении оснащения. Создание упражнения не добавляет оборудование залам.
- **Тяжёлые вычисления** (пересчёт аналитики) уводятся с Main через
  `flowOn(@ComputeDispatcher)` — в тестах квалификатор подменяется тестовым диспетчером.
- **Карточка упражнения.** Маршрут `exercise_detail/{exerciseId}` открывается из активной сессии,
  редактора программы, истории, итогов, аналитики и по info-кнопке библиотечного пикера.
  `ExerciseDetailViewModel` реактивно объединяет каталог, карту мышц и плоский поток завершённых
  подходов `WorkoutDao.observeCompletedSets()`. `ExerciseStatisticsCalculator` на compute-диспетчере
  группирует подходы по тренировкам: e1RM для силовых, суммарное время для timed и расчётную
  дистанцию для cardio. Активная незавершённая тренировка в карточную статистику не попадает.
- **Карточка зала.** Маршрут `gym_detail/{gymId}` отделяет просмотр от редактора.
  Оснащение приходит из конфигурации зала, доступные упражнения — из
  `GymRepository.observeAvailableExercises`, с теми же правилами покрытия оборудования,
  что в библиотеке. Пользовательский зал открывает редактор отдельным действием;
  стандартный допускает только просмотр и явное создание личной копии.
  Стандартные залы и программы находятся в свёрнутом разделе «Встроенные» над личными записями.
- **Карточка программы.** Маршрут `routine_detail/{routineId}` читает реактивный снимок
  `RoutineDao.observeRoutinesFull()` и показывает залы, упражнения, плановые подходы и отдых
  без редактирования. Личная программа открывает редактор отдельным действием, встроенная
  остаётся только для просмотра и копирования. Прямой вход в редактор встроенной программы
  также не предоставляет мутаций; ViewModel проверяет происхождение и готовность состояния
  перед изменением черновика, включая возврат из библиотеки упражнений.
- **Клонирование программ и залов.** Общий диалог запрашивает имя до записи. Репозиторий
  создаёт личный объект с новой идентичностью одной транзакцией: программа сохраняет
  упражнения, подходы, отдых и залы; зал — оснащение, legacy-связи и режим инвентаря.
  Исходный объект не изменяется, синхронизация планируется после успешного сохранения.
- **Публичные ссылки программ.** Личная синхронизированная программа может получить
  неизменяемую серверную ссылку. Android создаёт её только с account-head из `SyncReady`, а
  предпросмотр получает лишь allowlisted снимок без автора, залов, заметок или истории.
  Импорт принадлежит серверу и идемпотентен по receipt; клиент затем только читает `/sync` и
  применяет удалённую программу обычным `BackendSync`-слиянием, не клонируя её в Room. Маршрут
  `routine_share/{token}` доступен без входа через отдельную exported Activity со строгой
  HTTPS-проверкой; все остальные маршруты остаются за `AccountGate`.
- **Правки подходов** идут через `WorkoutSetMutator` и общий `WorkoutWriteQueue`: каждый шаг
  читает свежую строку, преобразует и записывает её в одной Room-транзакции. `WorkoutEditor`
  закрывает пользовательский подход, фиксирует строку и перед освобождением очереди запускает
  разрешённый настройками отдых.
- **ИИ-черновики.** Существующие действия упражнения/InBody используют авторизованные
  backend endpoints. Android отправляет намерение и подтверждённые ревизии; историю и контекст
  собирает сервер. `SyncReady` привязывает действие к владельцу, сессии и поколению локального
  кэша. Ответ проходит строгую DTO-валидацию; поздняя смена контекста блокирует применение,
  в том числе после чтений DAO перед открытием редактора. AI POST не повторяется после 401.
  InBody требует актуального разрешения того же владельца до кодирования и загрузки фото.
  `HealthAiDisclosureRepository` хранит receipt, точные байты очереди и последнее намерение
  пользователя; отзыв сразу запрещает передачу и доставляется после завершения старого запроса.
  Прямой клиент провайдера, BYOK-настройки и AI logger удалены; прежние секреты очищаются,
  а их исключения из backup/transfer сохраняются. Оба сценария создают редактируемый черновик;
  предметные данные Room меняются после явного сохранения пользователем.

## База данных

Схемы Room хранятся в `app/schemas/`, актуальная версия указана в `GymDatabase`.
Все миграции рукописные — `fallbackToDestructiveMigration` запрещён. Замеры тела лежат отдельно в `body_measurements`: все
показатели nullable (пропуск не равен нулю), а масса жира и WHR при отсутствии явного
InBody-значения вычисляются из сохранённых показателей. В v5 добавлены фактические поля полного
отчёта и фиксированные nullable-поля пяти сегментов; ID, пол, возраст, рост, цели контроля веса,
калории упражнений и импеданс в модель не входят.
В v7 у программ появились независимые от SQLite auto-ID `syncId` и монотонный `updatedAt`: они
связывают снимки пользовательской программы между установками и разрешают конфликт по более новой
версии.
В v8 такие же переносимые идентификаторы получили упражнения; встроенные UUID детерминированы
названием. Добавлены `gyms`, `gym_exercises`, `routine_gyms` и `workout_gyms`. UI работает через
`GymRepository`, поэтому будущий серверный транспорт не меняет экраны и доменные правила.
`configuration_tombstones` служит durable outbox удаления залов и программ: запись создаётся
одной транзакцией с удалением и исчезает только после подтверждённой выгрузки.
В v14 добавлены оснащение залов, требования упражнений и явное состояние перехода старых
конфигураций. Миграция сохраняет идентичности и историю; неизвестные требования своих
упражнений не превращаются в пустые. Встроенный справочник оборудования использует стабильные
ID, а каждое каноническое упражнение имеет явную разметку; прежние метки покрытия её не заменяют.
Выбор всего сохраняет снимок текущего справочника и не подписывает зал на будущие добавления.
Посев встроенного каталога упражнений идемпотентен и живёт в `onOpen`
(`GymDatabaseCallback`); карты мышц досеиваются `ExerciseMuscleSeeder`-ом.
Скрытый из пользовательских настроек legacy-экспорт (`DatabaseExporter`) делает `wal_checkpoint(TRUNCATE)` и копирует `gym.db`
в выбранный через SAF документ; очистка (`ClearDataUseCase`) стирает предметные таблицы,
пересеивает каталог и сохраняет metadata синхронизации для доставки удалений на сервер.

В v22 заметка подхода хранится в `workout_sets.note`, а личная подсказка упражнения —
в отдельной `exercise_personal_hints` по стабильному exercise syncId. Подсказка доступна
и для встроенных упражнений без изменения каталога. Узкие DAO-записи текста сохраняют
числовые изменения подхода; незавершённый подход с заметкой остаётся в истории, но не
попадает в копируемую программу. Черновик подсказки привязан к владельцу и сессии.
Синхронизация согласует `annotated-workout-writes` и `exercise-hint`; потеря поддержки
сохраняет личные данные и точные байты уже созданной очереди до её подтверждения.

В v23 базовый профиль хранится в `profiles`, а выбранное оборудование — в
`profile_equipment`. Пустой профиль не создаёт строку до сохранения; очистка полей
сохраняется как пустой снимок. Редактор проверяет владельца и эпоху сессии, при первом
переносе гостевой профиль получает устойчивый UUID владельца. Перед явным AI-действием
`AiProfilePromptGate` может предложить заполнить профиль: резервирование, показ и
однократное продолжение разделены, а период повторного предложения считается от
фактического показа. Черновик AI-запроса в этом журнале не хранится.

## Фоновые механизмы

- **WorkoutSessionService** — foreground-сервис активной тренировки: одно promoted-ongoing
  уведомление (Live Updates, Android 16) в двух состояниях (рабочий подход / отдых) с
  контекстными действиями и инлайн-правкой «60x8». Отсчёт в чипе рисует система
  (`setChronometerCountDown` + дедлайн по стенным часам), поэтому `RestTimerEngine` хранит
  дедлайн, а не остаток. `START_NOT_STICKY`: после смерти процесса сессию не восстановить,
  и «зомби»-уведомление хуже отсутствия (осознанное ограничение).
- **RestTimerEngine** — чистый Kotlin с инжектируемыми `WallClock` и `CoroutineScope`
  (в тестах — виртуальное время); тики пересчитываются от дедлайна, поэтому заморозка
  процесса (Doze) самокорректируется.
- **BackendSyncWorker** — фоновая синхронизация с собственным backend. Очередь и версии
  переживают смерть процесса; сетевые ошибки повторяются с backoff, конфликты показываются
  пользователю. Старые Upload*Worker совместимы с уже поставленной очередью через адаптер.
- **Обновление приложения** не использует периодический worker: release-сборка один раз за
  запуск процесса запрашивает публичный `GitHub Releases /latest`, а из настроек проверку можно
  повторить вручную. `AppUpdateViewModel` общий для оболочки и экрана настроек, поэтому
  скачивание и прогресс не теряются при навигации. Выбор «Позже» живёт до смерти процесса;
  «Не напоминать» сохраняет тег в DataStore и не скрывает следующий тег.
- **Восстановление недельного расписания** — уникальная цепочка
  `weekly_schedule_recovery` без network constraint и с `APPEND_OR_REPLACE`: worker может офлайн
  завершить локальный terminal marker, а при реально нужной сети возвращает retry. Успешная
  авторизация в настройках вызывает отдельный `wake()` с `REPLACE`, чтобы recovery продолжился
  сразу, а не ждал прежний exponential backoff. Активный шаблон остаётся SSOT в
  `settings.preferences_pb`, а отдельный machine-local journal хранит фазу `CREATE_NEW`,
  `CLEANUP_NEW` или `DELETE_OLD`. Новые Calendar event ID заранее генерируются как 32 lowercase
  hex и повторяются после смерти процесса; insert 409 и delete 404/410 подтверждают
  идемпотентный шаг. Terminal marker сначала локально применяет целевой active snapshot и только
  затем очищает journal. Один singleton repository `Mutex` сериализует UI и worker. Journal
  исключён из backup/device transfer, а active хранит nullable `ownerEmail`; legacy owner adoption
  остаётся эвристикой, после которой OAuth token всегда запрашивается для конкретного аккаунта.

## Обновление APK

`GitHubAppUpdateRepository` принимает только stable SemVer-тег и asset с детерминированным именем
`ValerochkaGym-v<versionName>.apk`. Потоковое скачивание идёт в `cache/app_updates`, ограничено
100 МБ и завершается только при совпадении размера и SHA-256 из GitHub API. Затем
`AndroidAppUpdateInstaller` проверяет package name, `versionName`, строго больший `versionCode` и
криптографически подтверждённую подпись APK против подписи установленного приложения. Лишь после
этого байты private-файла записываются прямо в `PackageInstaller.Session`: наружу не публикуется
ни файл, ни `content://` URI. Сессия помечается как пользовательская установка скачанного файла,
содержит исходные GitHub URL и всегда требует явного подтверждения. `Session.commit()` возвращает
статусы через приватный mutable `PendingIntent`; `STATUS_PENDING_USER_ACTION` передаёт системный
экран подтверждения, а блокировки и ошибки преобразуются в безопасный для UI текст. Такой путь не
зависит от передачи URI-grant между внутренними компонентами установщика ColorOS/OxygenOS.

Android требует специальный доступ «Установка неизвестных приложений» именно для ValerochkaGym:
если его нет, UI открывает `ACTION_MANAGE_UNKNOWN_APP_SOURCES`, а после возврата продолжает
установку. Сама установка всегда остаётся явным системным подтверждением пользователя.

Workflow на `main` собирает APK постоянным release-ключом, запускает тесты, проверяет `apksigner`
и создаёт `v<versionName>` только при отсутствии такого GitHub Release. Поэтому обычный коммит без
увеличения версии не становится обновлением, а уже опубликованный бинарник не перезаписывается.

## Backend и Google Calendar

`data/backend/BackendApi` обращается только к `https://api.valerochkagym.tech/v1`.
Случайные access/refresh-токены сохраняются через AtomicFile в noBackupFilesDir с AES/GCM
и неэкспортируемым ключом Android Keystore. Refresh сериализован Mutex и не очищает
новую сессию при запоздавшем отказе старого refresh-запроса. Email-вход включает регистрацию,
подтверждение и восстановление пароля. Кнопка Google использует Credential Manager с
`GetSignInWithGoogleOption` и серверным nonce; ID token проверяется на backend. Оба способа
входа проходят через `BackendSync.signIn`, без переноса локальной истории. Отмена выбора
Google-аккаунта закрывает диалог без ошибки.
Справка: https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation

Room v15 добавляет `backend_state`, `backend_baseline`, `backend_outbox`. SQL-триггеры
помечают изменения вместе с исходной транзакцией. `PortableData` преобразует числовые
Room ID в UUID-ссылки доменных агрегатов. `BackendSync` сравнивает локальный снимок,
подтверждённую базу и сервер; сохраняет точный пакет до HTTP и не теряет более свежую
локальную правку при подтверждении старого пакета. Пересекающиеся правки требуют выбора
локальной/серверной версии. При входе другого пользователя `BackendSync.signIn` под mutex
очищает предметные таблицы, baseline и outbox, меняет owner в одной Room-транзакции,
восстанавливает встроенный каталог и только затем сохраняет новые токены. Первое присвоение
owner тоже очищает старую историю; переноса данных без аккаунта нет. Повторный вход того же
пользователя сохраняет кэш. Выход с устройства работает без сети. Удаление аккаунта очищает
его историю на устройстве после подтверждения сервером.

`BackendSyncScheduler` реагирует на Room invalidations, запуск приложения и периодический
WorkManager (15 минут, только сеть). Активная тренировка откладывает remote sync: сервис
использует локальные ID подходов, которые нельзя заменить во время тренировки.
Старые Upload*Worker сохранены ради уже поставленных работ и действуют через
`BackendUploadAdapter`; HTTP-транспорт Sheets перенесён исключительно в тестовые fixtures.
Очистка данных сохраняет owner/baseline/outbox, чтобы удаления ушли на сервер.

Google Calendar по-прежнему использует отдельный `GoogleAuthManager`, GMS AuthorizationClient
и только scope calendar.events. OAuth-согласие Calendar не запускает импорт истории.
Недельное расписание и журнал его восстановления остаются прежними. AI API тоже не меняется.

### Отдельное подключение Calendar (Room 17)

`CalendarAccountIdentity` разделяет предпочтительный Google email и проверенное подключение
Calendar. Успешный backend Google-вход обновляет только предпочтение; парольные сценарии
не меняют Calendar. Настройки отдельно выбирают аккаунт, получают согласие для точного email
и записывают подключение после непустого account-bound токена без resolution. В SavedState
сохраняются только вид операции, целевой email и непрозрачный nonce; повторные и запоздалые
callbacks не получают право записи. Проверка актуальности операции и запись подключения
выполняются на одной границе DataStore edit. Отключение отзывает только calendar.events
подключённого аккаунта и сохраняет backend-сессию, локальные записи и удалённые события.

Миграция16→17 создаёт `calendar_event_account_links`: новые one-off события имеют
неизменяемого нормализованного владельца, прежние строки получают `LEGACY_OWNER_UNKNOWN`.
Неизвестный владелец не восстанавливается догадкой и не допускает удалённой мутации.
Метаданные локальны и не входят в `PortableData`; изменение аккаунта во время HTTP
проверяется до локальной записи, а отмена также сверяет исходную пару schedule/link.

Weekly active/journal продолжают хранить прежний ownerEmail, но право работы проверяется
по текущему подключению Calendar. Финальная проверка owner и запись target расписания
проходят в одном DataStore edit; очистка журнала после успешной записи завершает уже
применённую операцию. При несовпадении владельца журнал сохраняется. Создание события
перед локальной транзакцией может оставить удалённое событие при локальном сбое;
автоматического удаления под другим аккаунтом нет.

## Интеграция с нейросетью

`BackendAiRepository` обращается к аутентифицированным `/ai/exercise-drafts` и
`/ai/inbody-drafts` собственного backend. Перед запросом `SyncReadySource` подтверждает
текущего владельца, сессию, поколение локального каталога и завершённую синхронизацию.
Эти границы повторно проверяются перед отправкой и применением ответа, в том числе после
чтения DAO для открытия редактора. POST не повторяется после 401.

Ответ проверяется по строгим DTO, requestId и исходному контексту. Упражнение открывается
как существующая запись или редактируемый черновик; InBody заполняет редактируемую форму.
Предметные данные сохраняются только после явного действия пользователя. Ошибки сервера
показываются через безопасные сообщения UI, без сохранения тела запроса, ответа или ошибки.

InBody требует отдельного текущего согласия `HealthAiDisclosureRepository`. Локальный
отзыв блокирует обработку сразу, включая время ожидания и кодирования фотографии.
Owner-scoped журнал согласия сохраняет точные байты запроса для повтора, а подтверждение
сервера не может затереть более новый локальный отзыв. Фотографии и AI-черновики в этот
журнал не попадают. Ручное заполнение замеров остаётся доступным.

Прямой клиент провайдера, выбор URL/модели, BYOK-настройки и AI logger удалены. Очистка
прежних секретов выполняется при переходе; новые ключи провайдера Android не хранит.

## Осознанные решения

| Решение | Почему |
|---|---|
| Zero-logging | ошибки видны в UI; AI-запросы, ответы и фотографии не записываются в диагностические логи |
| Predictive back — только системный | seekable-переходы Navigation Compose не подключены; пружинные слайды играют как обычные pop'ы |

## Общий каталог (Room 16)

`data/backend/CatalogSync` загружает публичный `/v1/catalog` до личного sync, включая
оборудование и архивы. Записи применяются по UUID в существующие Room-строки; числовые
ID и исторические связи сохраняются. `origin` различает `PERSONAL` и `STANDARD`.
Стандартные родители и вложенные конфигурации защищены SQLite-триггерами от личной правки.

`catalog_state` хранит независимую ревизию, активацию и журнал перехода;
`catalog_records` — общий baseline, `catalog_equipment` — определения оборудования.
Рабочая проекция `LocalEquipmentCatalog` загружается из БД и обновляется после commit.
APK-справочники применяются только для начального офлайн-заполнения. При повторном
открытии скачанный каталог и карты мышц не пересеиваются. Начальный снимок APK-заготовок
позволяет исключить неиспользуемые заготовки из отправки при чистом восстановлении аккаунта.

`PortableData.snapshot` исключает общие агрегаты из личных изменений, но сохраняет
UUID-ссылки на них. Конфликт перехода не очищает исходный outbox. Выбор в настройках
аккаунта сохраняет правки личными копиями с новыми UUID либо принимает стандартные версии;
исторические тренировки автоматически не переключаются на копии. Журнал переживает
перезапуск приложения и входит в экспорт SQLite. Очистка личных данных сохраняет каталог.

Активная тренировка откладывает применение обоих потоков. Новый клиент передаёт
`X-Gym-Sync-Version: 2` и `catalogRevision`. При `catalog_stale` сначала обновляется каталог,
затем новая операция сохраняется в outbox до повторного HTTP-запроса.

## Владение локальными данными и первичный перенос (Room 18)

`backend_state` хранит GUEST → CLAIMED(owner, mergeId) → OWNED. Claim фиксируется
в Room до записи токенов; после сбоя возобновить перенос может только тот же owner.
Первичный перенос завершается после ACK всех пакетов, пустого outbox и свежего
сравнения локального снимка с подтверждённым baseline. При замене существующего
владельца preflight проверяет полные portable/baseline данные, exact outbox и
catalog journals, applying state и tombstones; неоднозначные данные сохраняются.

`backend_rejected_operations` отличает определённый revision-conflict от потерянного
ответа: отклонённые bytes сохраняются, но не отправляются повторно до разрешения
конфликта и создания новой операции. `backend_conflict_copies` связывает конфликт
программы с одной устойчивой полной локальной копией; baseline копии появляется
только после её собственного ACK. Конфликт завершённой тренировки принимает один
серверный снимок, остальные неоднозначные конфликты требуют явного выбора.

BackendSync проверяет owner/phase/token на сетевых и транзакционных границах,
включая применение каталога. Account-management цепочки выполняются через
`accountRequests`: один captured owner и mutex на все запросы и commit результата.
ViewModel хранит список сессий вместе с owner и не показывает его другому аккаунту.
Исторический `SyncSchema.create` остаётся контрактом 14→15; новые таблицы создаёт
соответствующая рукописная миграция или генерация свежей Room-базы.

## Завершение локального пакета (Room 26)

`data/trainingproposal` хранит личный AI draft и неизменяемые байты подтверждения. Принятый
сервером результат проецируется через полный
`BackendSync` в одной Room-транзакции с marker; обычный outbox сохраняется.

`data/ai/WorkoutPreparationRepository` сохраняет owner-scoped заявку в Room 27 до закрытия
формы. WorkManager доставляет точные байты короткого POST `/ai/calendar-draft-jobs` после
`SyncReady`, затем получает статус через GET. UUID и ancestry исключают повторную генерацию
после потерянного ACK и публикацию заменённой заявки. Серверная SQL-очередь и lease продолжают
расчёт без клиента и восстанавливают прерванные исполнения.

Карточка на едином экране планирования читает Room, различает ожидание отправки, серверный расчёт, готовность,
ошибку, устаревание и истечение даты. Фоновые повторы ограничены; после исчерпания явное
действие продолжает тот же запрос. Foreground refresh также ограничен. Старое готовое
предложение остаётся доступным при пересчёте, журнал ручных правок не перезаписывается.
`CalendarAiRepository` проверяет typed результат и локальную актуальность; перед новым
подтверждением PLAN01 проверяет generation, сервер — current job, ревизии и исходную дату.
Создание программы и календарного плана остаётся исключительно за явным подтверждением.
История и provider payload на клиенте не формируются; health ledger в этот контракт не входит.
Форма подготовки не запускает дополнительный обязательный onboarding.

`SyncReady.Blocked` при подготовке трактуется как временная неготовность синхронизации,
а не как окончательное устаревание предложения. Изменение локального `generation` само по себе
не переводит выполняющуюся заявку в STALE. Перед валидацией READY устаревшая квитанция может
быть заново подтверждена через `SyncReadySource.await`: owner, session epoch и обе серверные
ревизии должны совпасть, затем повторяется полная локальная проверка. Изменившиеся серверные
ревизии по-прежнему отклоняют результат. `retryCurrent(expectedId)` повторяет сохранённое
намерение в транзакции с проверкой аккаунта и текущей заявки: после сетевой паузы сохраняет
идентичность и байты, после STALE создаёт новую заявку с ancestry. Истёкшая дата не переносится
автоматически. Экран повторно запускает ограниченный refresh при переходе пауза → ожидание,
даже если UUID не изменился.

UI-редактор недельного расписания удалён. Хранение и синхронизация ранее созданных правил
сохраняются; пользователь может управлять отдельными занятиями из выбранного дня.
Новые разовые планы из программы создаются на общем экране планирования через прежний
CalendarPlanRepository, с блокировкой повторного запроса до завершения операции.
Чтение списка, детали и результата предложения допускает штатное обновление авторизации
после 401; операции подтверждения и отклонения не повторяются автоматически.

Проверка на эмуляторе выявила серверную причину `ai_context_stale` для встроенного зала:
`AiContextReader.captureCalendar` искал gym только в персональных records. Исправление бэкенда
`fix/calendar-standard-gyms` добавляет ограниченную выборку активных standard_records для
запрошенных залов, отсутствующих среди личных. Новая серверная регрессия проверяет полный
маршрут фоновой задачи до READY; архивные и отключённые каталожные залы остаются недоступны.
До публикации серверного исправления расчёт со встроенным залом на production может
по-прежнему отклоняться — клиентская кнопка повтора сама этот дефект сервера не устраняет.



## Live Coach: контракт реализации

Согласованное поведение и приёмка: `vibe/live-coach-product.md`, исполняемый план и результаты
проверок: `vibe/live-coach-plan.md`, `vibe/live-coach-plan-track.md`.

Live Coach относится к активной тренировке. Его контекст ограничен тренировкой, каталогом,
оборудованием, мышцами, отдыхом, свежим доступным пульсом и историей упражнений. Замеры тела и InBody
не входят в этот контур. Исходная программа не меняется. `BackendCoachModelGateway` передаёт
ограниченный model turn в `/v1/ai/coach-turn/stream`, с закреплёнными owner/session epoch, без SyncReady
для ещё локальной активной тренировки. Сервер хранит ключ и allowlist моделей; отдельная модель
тренера выбирается из `/v1/ai/coach-models` и сохраняется локально для аккаунта. Формат и ограничения —
`vibe/live-coach-server-contract.md`.

Приложение принимает типизированный пакет операций, а не исполняемый код модели. Точная локальная
команда получает внутреннее разрешение на весь пакет с закреплёнными UUID подходов. Остальные
изменения требуют сохранённого предложения «было → станет». Проверка аккаунта, активности,
принадлежности объектов, ревизии и повторного operationId выполняется перед записью. Весь пакет
и его результат должны сохраняться атомарно. Незавершённая часть заменяемого упражнения переносится
отдельно от выполненных результатов; если выполненных подходов нет, исходная секция удаляется,
а замена занимает её позицию. Рабочий вес другого упражнения не переносится автоматически.
Промпт предпочитает знакомые упражнения и предлагает модели оценить стартовый вес нового
упражнения по сопоставимым результатам, явно обозначив оценку и передав её в предложение.
Если у силового упражнения для замены нет собственной истории и вес не задан явно, предложение
сохраняет неизвестный вес. Ошибка подготовки предложения отличается от конфликта ревизии.
При конфликте ревизии без записи приложение возвращает модели актуальный снимок для одной
попытки исправить запрос в пределах текущего ограниченного агентского цикла. Смена аккаунта,
сессии или остановка запроса не разрешает повтор. Сохранённое предложение завершает цикл
и по-прежнему требует подтверждения пользователя. Устаревший пакет не применяется автоматически.

`CoachWorkoutReader` только читает снимок, каталог и историю; `CoachToolCodec` форматирует ответы
инструментов. `WorkoutEditor` готовит операции, фиксирует вес замены и последовательно рассчитывает
пакет на локальной копии всех полей секций и подходов (`RestoreSection`/`RestoreSet` — существующий
формат полного undo). `WorkoutChangeSummary` только форматирует рассчитанные состояния шагов.
Предпросмотр не пишет тренировку и не запускает отдых; подтверждение повторяет тот же расчёт
в транзакции на проверенной ревизии. Сохранение сравнивает UUID глобально по тренировке: сначала
создаёт новые секции, переносит/обновляет подходы с прежними Room ID, затем удаляет лишние строки.
Undo проходит через этот же расчёт и сохранение.
Сообщение о занятом тренажёре ведёт сразу к предложению подходящей перестановки или замены.
Отдельного списка занятости в состоянии тренировки и инструментах модели нет.
`CoachConversationService` атомарно хранит сообщения, контекст, журнал и инициативу с повторной
проверкой аккаунта, session epoch, активности и идентификатора запроса перед коммитом; квота
инициативы проверяется вместе с актуальной ревизией и контекстом. Сеть работает вне очереди.

Агентский цикл управляется существующим сервисом тренировки; сетевые запросы не удерживают очередь
изменений. Завершение занятия и остановка сервиса прекращают дальнейшее исполнение. Диалог и уже
применённые команды сохраняются локально; после смерти процесса незавершённый запрос становится
прерванным и не повторяет инструменты. Таймер и пульс остаются данными текущего процесса.

Серверный контракт журнала — backend PR #7, `POST/GET /v1/coach/journal` с протоколом 3.
События неизменяемы и идемпотентны по UUID. Журнал разрешено отправлять только после подтверждения
актуального переносимого снимка тренировки, включая её ревизию; старый outbox повторяется с исходным
содержимым и operationId. Импортированный журнал служит историей, а не разрешением выполнять
команды. Курсор аккаунта фиксируется после полного прохода страниц. Первые данные протокола 3
требуют обновить остальные клиенты этого аккаунта.

Обновление с ранней сборки Live Coach учитывает коллизию номера Room 17 с календарной схемой
main. Ручные миграции восстанавливают недостающие календарные связи с неизвестным владельцем,
сохраняют заполненные UUID подходов и существующий журнал. Перекрывающиеся столбцы приводятся
к SQL defaults схемы 28 без пересоздания родительских таблиц; контекст тренера дополняется
с сохранением уже известных значений. Регрессия: `MigrationLegacyLiveCoach17To28Test`.

Самая ранняя установленная схема Room 17 содержит другой формат пяти таблиц тренера.
`LegacyCoachArchiveRegistry` распознаёт этот формат и сохраняет таблицы под именами
`legacy_live_coach_v1_*` до создания текущих таблиц. Архив не предоставляет разрешений на
изменения и не участвует в синхронизации текущего журнала. Он сохраняется в полной копии БД
и при обычном выходе из аккаунта; очистка данных и смена владельца удаляют архив через общий
реестр. Удаление тренировки каскадно удаляет её старые сессии, предложения и журнал.
Регрессия `MigrationDeviceLegacyCoach17To28Test` использует фактическую схему устройства
из `legacy-coach-device-v17-schema.json` с искусственными записями.

Единая миграция 27→28 сразу создаёт финальную схему Live Coach. При восстановлении
раннего контекста она сохраняет его поля и убирает `occupiedEquipmentJson` из сохранённого undo;
повреждённое состояние undo отключается без потери тренировки. Ожидающие подтверждения
пакеты с удалённой операцией `SetOccupiedEquipment` целиком становятся `STALE`.
Исторические предложения, журнал и исходные байты outbox не переписываются.

Подтверждение Live Coach хранит локальный типизированный `WorkoutApprovalPreview` в
`coach_proposals.previewJson` (Room 28). `WorkoutApprovalFormatter`
сворачивает рассчитанные шаги в итоговые действия, используя UUID секций и подходов.
Карточка показывает замену с краткой нагрузкой, только изменённые поля подходов и
смысл перестановки; весь пакет по-прежнему применяется атомарно. Старые предложения
без предпросмотра читаются через сохранённые тексты. Серверный журнал не меняет формат.

Финальный текстовый ответ модели Live Coach (prompt v5) содержит JSON `text` и
`quick_replies` (0–4 короткие реплики пользователя). `CoachReply` отделяет текст от
вариантов, отбрасывает пустые, повторные и некорректные варианты; обычный текст старой
модели остаётся читаемым без кнопок. Room 28 содержит nullable
`coach_messages.quickRepliesJson` и `readAt` с первой схемы релиза Live Coach. Варианты сохраняются локально
для повторного открытия активного чата; серверный журнал по-прежнему получает только
видимый текст, без изменения протокола. История модели также содержит только текст.
Инструментальные результаты и подтверждения пакетов сохраняют существующий формат.

При `reorder_exercises` обязателен полный список секций, включая выполненную разминку.
Неполный/чужой список возвращает `InvalidOrder` без изменения тренировки;
сервис передаёт модели `invalid_exercise_order` и актуальный `current_state`. Исправление
делит единственный recovery-бюджет с конфликтом ревизии, после повторного отказа цикл
останавливается. Исправленный пакет всё равно требует подтверждения. Регрессия воспроизводит
перестановку семи оставшихся упражнений с пропущенной восьмой, выполненной разминкой.

Текущая версия Room — 28. Схемы и миграции до 27 включительно соответствуют main;

### Потоковый ответ Live Coach

`BackendTransport.authorizedEventStream` возвращает ограниченный SSE-поток с owner и session epoch.
`BackendCoachModelGateway` проверяет requestId/model/session перед каждым `TextDelta` и `Completed`.
SSE error завершает обмен; EOF без терминального события — обрыв.
При HTTP-ошибке открытия потока POST повторяется до трёх раз с паузами 1/2/4 секунды
и теми же байтами запроса. После начала SSE повторов нет; refresh самого потока,
redirect и fallback отключены. GET каталога моделей
перед потоком допускает один refresh и повтор при 401. Подтверждённая ротация credentials
сохраняет эпоху входа, поэтому не отключает диалог и открытый поток; явный save, выход
или новый вход меняют эпоху и прерывают старую работу. Refresh применим только к точному
исходному снимку и тому же владельцу. Лимиты — 4 MiB поток, 256 KiB событие,
60 секунд обмен и 180 секунд цикл. Отмена закрывает вызов и response body. Production sessionEpochs
сигнализирует даже явное сохранение равных credentials, чтобы старый запрос не пережил новую эпоху.

`CoachTextDecoder` инкрементально извлекает только верхнеуровневую строку text; служебные поля
не публикуются. Другие форматы ждут полного ответа и CoachReply.decode. Инструменты исполняются
исключительно из completed после прежней валидации. Черновик сбрасывается перед каждым новым
обменом и выполнением инструментов. `CoachConversationService.responseDrafts` принадлежит сервису,
а не экрану; содержит ID ответа/запроса/тренировки, account/epoch, текст и признак streaming.
При ошибке/отмене/смене сессии/завершении тренировки он удаляется. Успех сохраняется один раз в Room
с тем же ID; временная финальная копия остаётся до следующего запроса или остановки тренировки,
чтобы асинхронное обновление DAO не создавало пустой кадр. ViewModel предпочитает сохранённую запись
с таким ID. Сглаживание существует только в UI и не задерживает запись, инструменты или уведомления.
Подробности — `vibe/live-coach-streaming-plan.md` и `vibe/live-coach-server-contract.md`.

При принятом retry сообщение ошибки удаляется из локального диалога в одной транзакции
с переводом исходного сообщения пользователя в PENDING. Неизменяемый журнал сохраняется;
повторный импорт уже известного события не восстанавливает удалённое сообщение.
Новая неудача создаёт одну новую ошибку, сообщение пользователя не дублируется.

Промпт Live Coach загружается через авторизованный `GET /v1/ai/coach-prompt` перед каждым
ответом и остаётся неизменным на протяжении цикла инструментов. Статического fallback нет;
GET допускает refresh и повтор при 401; ошибка загрузки проходит через обработку ошибок CoachAgent. Бэкенд хранит текст
в БД и кэширует на 5 минут; редактирование доступно в настройках ИИ админки.

### Поиск и предзаполнение Live Coach

`find_exercises` объединяет фильтры названия, конкретных мышц, широких `muscle_groups`
и требований оборудования. До ограничения выдачи (10 по умолчанию, максимум 20) варианты
сортируются по дате последней завершённой тренировки, затем по числу тренировок.
Ответ содержит опыт использования, секции текущей тренировки и полный упорядоченный список
выполненных подходов последней завершённой тренировки, включая повторные секции упражнения.
Активные тренировки и незавершённые подходы исключаются. Даты завершения тренировок
передаются отдельно от nullable-времени выполнения подхода. `get_exercise_history`
предназначен для информационных сравнений и возвращает три завершённые тренировки.

При `add_exercise` редактор фиксирует исторические значения и типы подходов в пакете
предложения: при подтверждении история повторно не читается. Новые подходы получают
новые UUID, плановые значения и остаются незавершёнными, без заметок, фактических результатов
и самочувствия из истории. Без истории создаётся один пустой подход. Необязательная
`position` задаёт индекс вставки; по умолчанию упражнение добавляется в конец.
`replace_remaining` сохраняет прежнюю семантику оставшихся подходов и отдельную оценку веса.
Обоснование модели из верхнеуровневого `reason` показывается отдельно от рассчитанного
приложением описания ожидающего подтверждения пакета.

## Персонализация силового планирования (Room 30)

`strength_planner_profiles` и `strength_planner_key_exercises` хранят до пяти стабильных
UUID упражнений с приоритетами HIGH/NORMAL. Редактор доступен при цели STRENGTH. Профиль и
ключевые упражнения сохраняются одной транзакцией; устаревшую ссылку можно удалить, новый
выбор требует живого силового упражнения.

`workout_efforts` хранит необязательную оценку EASY/MODERATE/HARD; null явно очищает её.
Экран итогов фиксирует владельца и сессию до загрузки. Смена сессии до или во время записи
откатывает транзакцию. Наличие черновика хранится отдельно от его nullable-значения.

Оба независимых типа синхронизируются через capability `strength-planner-personalization`.
Старые payload профиля/тренировки не меняются. При отсутствии capability очередь сохраняет
точные байты; backend скрывает новые типы от старых клиентов и удаляет effort вместе с
родительской тренировкой. Миграция персонализации 29→30 рукописная; предшествующая 28→29 из main удаляет связи тренеров.

Для STRENGTH backend сначала применяет ограничения доступности, затем ранжирует до 24
кандидатов и задаёт обязательное основное упражнение. Компактный `strength-compact-v1`
содержит последние совместимые фактические вес/повторы для выбранных и ключевых упражнений
(до 29), объём/частоту за 7/28 дней и явную оценку усилия. Давние результаты ищутся отдельно;
null не заменяется плановым значением. Подробная история и масса тела в этот контекст не
попадают. AI не назначает вес; итог проверяется сервером, вес переносится из истории.
Остальные цели используют прежний путь. См. `vibe/strength-planner-personalization-plan.md`
и трекер для проверок и зависимостей перед публикацией.

Поле RIR активного силового подхода объединяет выбор усилия и явную разминку (`SetEffort`). Room 32 хранит «4+» отдельно (`actualRirAtLeastFour`, точный `actualRir = null`); диапазон проходит через backup/sync и undo. Отсутствие RIR/типа не инициирует вопросы live-тренера.

Целевой RIR исключён из активной модели и инструментов AI. `legacyTargetRir` сохраняет старую историю без участия в расчётах; авторегуляция 1.2.0 не вводит скрытую цель; сравнивает соседние подходы и пороги повторов, сохраняя отдельный путь явного сообщения о неожиданно тяжёлом усилии.

Live Coach 1.3.0: локальный сигнал → скрытый запрос в общей очереди → ИИ оценивает шаг → подтверждаемое предложение. Числа ИИ не обязаны совпадать с локальной эвристикой; автоматического применения нет. Приветствие отключено, границы повторов проверяются с первого рабочего подхода.


ИИ-запросы через BackendApi используют до трёх дополнительных попыток при HTTP-ошибках
(паузы 1, 2 и 4 секунды). Успешные 2xx, включая принятие фоновой задачи 202, повторов
не вызывают. Сетевые исключения, ошибки разбора и ошибки внутри SSE с HTTP 200 не
перезапускают запрос. Между попытками сохраняются тело и requestId; отмена и смена
сессии прекращают повторы. Для запросов с разрешённым обновлением авторизации
существующий refresh выполняется до обработки оставшейся HTTP-ошибки.
