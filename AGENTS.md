# AGENTS.md

Персональное Android-приложение для силовых тренировок. Один модуль `:app`.
Обзор слоёв и решений — [ARCHITECTURE.md](ARCHITECTURE.md); правила UI —
[docs/design-system.md](docs/design-system.md) (источник правды, читать перед любой UI-работой).

## Команды

```bash
./gradlew :app:testDebugUnitTest      # все unit-тесты (JUnit4 + Robolectric)
./gradlew :app:assembleDebug          # debug-сборка
./gradlew :app:assembleRelease        # release: R8 + сжатие ресурсов (без подписи)
./gradlew :app:testDebugUnitTest --tests "*ИмяТеста"   # один класс
```

## Стек и версии

AGP 9.x со встроенным Kotlin — плагин `kotlin.android` НЕ применять. Material3 закреплён
alpha-версией поверх Compose BOM ради Expressive API (`MaterialExpressiveTheme`,
`motionScheme`). Hilt + KSP (без kapt). Версии — только через `gradle/libs.versions.toml`.

## Правила кода

- **Строки UI хардкодятся в Kotlin** (решение владельца): приложение одноязычное,
  `strings.xml` — только `app_name` и OAuth client ID. Не выносить тексты в ресурсы.
- **Room — только рукописные миграции** (схемы в `app/schemas/`), destructive fallback запрещён.
- **Моушн — только токены `GymMotion`** (`ui/theme/Motion.kt`); инлайновые `spring`/`tween`
  в экранах запрещены. Сторонние анимационные библиотеки и библиотеки графиков не добавлять.
- **Хаптика — только семантика `GymHaptics`** (`gymHaptics()`), не сырой `performHapticFeedback`.
- **Цвета — только `MaterialTheme.colorScheme.*`**; хардкод `Color(0x…)` вне `ui/theme/` запрещён
  (исключение — шкалы данных `ChartPalette`, см. design-system §3).
- Диагностика Live Coach — через `CoachDiagnostics`, тег Logcat `LiveCoach`, только debug.
  Логировать этапы, числовые параметры расчёта, причины решений и типы/места ошибок.
  Не выводить переписку, промпты, полные tool arguments, снимки данных, токены и данные аккаунта.
  Для остальных подсистем новое логирование без отдельного запроса не добавлять; ошибки
  по-прежнему показываются в UI.
- Тяжёлые вычисления в потоках — через `flowOn(@ComputeDispatcher)`, чтобы тесты могли
  подменить диспетчер.

## Тесты

- JUnit4, имена — backtick-предложения в настоящем времени:
  `` fun `completing a set marks it done and starts rest`() ``.
- **Рукописные фейки, приватные в файле теста** — мок-библиотек в проекте нет и не будет.
- ViewModel-тесты: `MainDispatcherRule` + `runTest(mainDispatcherRule.testDispatcher.scheduler)`;
  `stateIn(WhileSubscribed)` холодный — перед чтением `uiState.value` цеплять живой
  коллектор (хелпер `collectUiState`). Образец: `ui/WorkoutsViewModelTest.kt`.
- Robolectric — только где неизбежен Android (DAO — база `RoomDaoTest`, воркеры, рендер);
  закреплён `sdk=36` (`app/src/test/resources/robolectric.properties`), тестовый JVM — JDK 21.
- Тесты приватных методов не писать.
- При UI-тестировании по умолчанию использовать accessibility-дерево, UIAutomator/ADB,
  Compose-тесты и фильтрованный `logcat`. Не создавать, не запрашивать и не анализировать
  скриншоты или видеозапись без явной просьбы пользователя; если без визуальной проверки
  продолжить нельзя — сначала запросить разрешение.
- Проверка стадии работы: полный `testDebugUnitTest` + `assembleDebug`; после правок
  графиков запускать `AnalysisRenderTest`, а его снимки в `app/build/reports/analysis-render/`
  открывать и анализировать только по явной просьбе пользователя.
- Полный прогон Gradle выполнять только при изменениях кода приложения или сборочной
  конфигурации: `app/**`, корневые `*.gradle.kts`, `gradle.properties`, `gradle/**`, `gradlew*`,
  `buildSrc/**` или `build-logic/**`. Для правок только документации, планов, `AGENTS.md`,
  Git/GitHub-конфигурации или CI-файлов тесты и сборку не запускать без явной просьбы.

## CI

- Android CI, AI code review, Gradle-тесты и публикация релиза должны выполняться только при
  изменении кода приложения или сборочной конфигурации из списка выше. Документационные и
  организационные правки сами по себе не должны запускать сборку, тесты, AI-review или релиз
  и не требуют новой версии.
- Для pull request допускается только лёгкая проверка списка изменённых файлов, необходимая для
  обязательного статуса защиты `main`; при отсутствии кодовых изменений она должна завершаться
  успешно без checkout репозитория, настройки JDK/Gradle и запуска тестов.

## Версионирование

- Каждая завершённая фича или исправление должна содержать один инкремент версии приложения
  в `app/build.gradle.kts`: `versionCode` увеличить на 1, patch-компонент `versionName` — на 1.
  Minor/major повышать только по явному указанию пользователя.
- Перед финальным коммитом или push feature-ветки и перед выполняемым Codex слиянием pull request
  в `main` проверять версию относительно целевой ветки. Если инкремента нет — добавить его; если
  он уже сделан для этой фичи — повторно версию не повышать.
- Если целевая ветка успела получить более новую версию, до push/слияния устранить конфликт так,
  чтобы `versionCode` и `versionName` были строго выше актуальных значений целевой ветки.
- Самостоятельно выполнять push или слияние это правило не разрешает: для внешнего изменения
  по-прежнему нужен явный запрос пользователя.

## Git

- Перед внесением изменений проверить текущую ветку, `git status`, последние коммиты и отличие
  от целевой ветки; сопоставить назначение ветки с запрошенной доработкой.
- Продолжать работу в текущей ветке только когда она относится к той же фиче или исправлению.
  Если открыта `main`, release-ветка либо ветка другой задачи, до внесения изменений создать
  отдельную ветку от подходящей актуальной базы с префиксом `feat/`, `fix/`, `chore/` или `docs/`.
- Не переносить в новую ветку и не смешивать с задачей ранее существовавшие незакоммиченные
  изменения неизвестного назначения. Если безопасно отделить их нельзя — остановиться и
  запросить решение пользователя.
- Явное указание пользователя работать в конкретной ветке имеет приоритет. Создание локальной
  ветки не разрешает её push: внешняя публикация по-прежнему выполняется только по запросу.
Сообщения коммитов — на русском, со смысловым префиксом (`feat:`, `test:`, `refactor:`,
`perf:`, `build:`, `chore:`, `docs:`). Планы работ и трекеры — в `vibe/`
(`<имя>-plan.md` + `<имя>-plan-track.md`).
